# ネイティブ GNU Shogi の動作・棋力条件調査

調査日: 2026-11-07。実施中の対局設定やバイナリは変更していない。検証用のエンジンは別プロセス・CPU affinity 指定で動作させた。ただしホストの負荷や周波数は厳密には隔離していない。

## 対局の設定・時間

- 原版 1.2p03 と互換パッチのネイティブ x86-64 バイナリ SHA-256 `dabd529e07ba91a66b69abbbbe2476ea358fd125fc3ec331346e45cea7c2e5b9`。GCC 11.4、`-O2 -funroll-loops -std=gnu89 -fcommon -fgnu89-inline -DLONG64`。探索を複数スレッド化する実装は原版中には見当たらず、実プロセスも1スレッド。
- 両者とも定跡・ponder無効。GNU側の `USI_Hash=2` は互換用で、実際のGNU内部ハッシュ容量を2MiBに設定していない。1回の探索上限は `level 0 0:10`。対局側は送信手順を合法性検証し、GNU側の盤・持駒・手番・手数を毎回読戻して照合する。ただし内部の全状態が原版の通常対局と完全に同じことまで保証しない。
- 調査時のGNU着手108手中99手は8秒以上、9手は1秒未満、中央値9998.2ms。早い手の一例では内部ログが相手の3手詰めを出力しており、対応するソースにも詰み等で探索を早期終了する処理がある。詰み判定自体の正しさを独立に全検証したわけではない。
- 例の `Hin/Hout` はすべて0だが、これは表が無効という意味ではない。原版のMakefileは `utilR.o` を `-DBAREBONES` で作るためカウンター更新を省く。探索コードに計数だけを追加したコピーで対象局面を深さ5で実行したところ、局面表の書込み25967回、ヒット5864回。探索結果・ノード数は元バイナリと同じ。
- 同じ `BAREBONES` の影響で `TTadd` の増加も省かれる。アダプターは毎手 `new` と手順再生を行うが、`new` の条件付き局面表初期化は `TTadd=0` のため実行されない。前手の表が残り得る。検証用の3連続局面・深さ5では、新プロセスで毎局面を探索した場合と選択手は3/3一致し、2局面目のノード数は残存あり1697153、毎回再起動2007665、3局面目は292205対515869だった。残存表は結果や探索速度に影響しうるため、再現条件として明記する。アダプターが局面を毎回再構築すること自体、原版の通常の連続対局と内部状態が完全に一致する保証にはならない。

## ビルド・原版の条件

- 比較用の32bit musl静的版（現代クロスコンパイラ、定跡無効）は、開始局面3つと対局途中1つの深さ5指定で、64bit版と4/4同一手だった。ノード数は完全一致せず、途中局面では両方とも深さ4で早期終了。10秒指定の2局面でも2/2同一手だった。32bit版は10秒あたり約467万・625万ノード、64bit版は約628万・865万ノード。各1回でコンパイラやlibcも違う参考試験であり、移植の正しさや全局面の速度差を証明しない。32bit検証バイナリの SHA-256 は `05eadcc58619f6f48a5dc8c6a8586e38942a7245d57b864064eb0b9819b55d25`。
- 同じ64bitソースで `-O3 -march=native` を試すと、上記深さ5の手とノード数は4/4一致。10秒探索の2局面は約616万・857万ノードで、`-O2` の約628万・865万とほぼ同程度だった。各1回で測定負荷も変わり得るため、最適化で強くなる・ならないとは断定できない。
- 原版 `search.c` は `capture` フラグ値512を `signed char` 型の `CptrFlag` に格納する。現在の環境では0になり、直近の駒取りを見て探索を延長する条件が成立しない。これは本移植の追加改変ではなく、原版にもある。検証用コピーで真偽値に直した場合、開始局面1で深さ5の手が `3i4h` から `4i3h` に変わり、ノード数は1066188から2337572へ増えた。10秒でも同じ手の違いが出た。開始局面2では10秒時に `4f4e` から `P*2d` に変化した。別の2局面では深さ5の手は変化しなかった。この短い検証は、修正版の方が強いことを示していない。修正は探索内容を変更するため、原版の結果とは別条件で扱う。

## 結論と残る限界

1スレッド、10秒探索、局面表使用という点で、設定による明白な縛りは確認されなかった。64bit版と32bit版の少数の結果はおおむね整合するが、「移植に一切問題がない」「今のPCで到達できる最大棋力」とは証明できない。原版の探索延長に見つかった問題は強さに影響する可能性があり、原版尊重と修正版の性能を分けて比較する必要がある。既存の対局は原版相当のまま継続し、修正版を混ぜない。詳細なプロトコルと検証結果は `.local/native-gnu-audit/`、本番結果は `.local/native-gnu-evaluation-20261107/` にある。
