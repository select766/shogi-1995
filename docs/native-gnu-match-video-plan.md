# GNU Shogi ネイティブ対局・撮影の実装計画

更新: 2026-11-07。レビュー内容を反映。86Box を使う試験は進行中の測定を避ける。

## 目的と条件

1995年の GNU Shogi 1.2p03 を現代 Linux ホストでネイティブ実行し、86Box 上の Pentium 100 MHz / Linux 1.2.13 で動くやねうら王と自動対局する。ゲスト内の既存GUIに盤面・棋譜・結果を表示する。GNU は探索・時間確認を改造せず、ビルドと接続に必要な互換修正を分離して記録する。

各手は独立して10秒を指定する。やねうら王には `go btime 0 wtime 0 byoyomi 10000`、`NetworkDelay=0`、`NetworkDelay2=0` を設定する。GNU には起動後に `level 0 0:10` を指定する。多少の超過は認め、着手を時間切れ負けにしない。各手の経過時間と超過を記録する。応答が戻らない異常状態については十分長い運用タイムアウトを別に設け、勝敗ではなく異常終了にする。具体値は試験結果に基づき設定・記録する。定跡・ponder は両者オフを初期条件とする。

やねうら王はその時点で最強と判断したビルド・モデルを明示指定する。候補はまだ確定していないため、設定とイメージ生成を分離し、後から差し替え可能にする。各実行でバイナリ・モデル・設定・ゲストイメージのハッシュを保存する。同一シリーズの途中で変更しない。

結果は現代ホスト上の1995年ソフトと、1995年相当の仮想マシン上の現代エンジンの比較であり、同一ハードでの比較ではない。厳密な上限制御や論文水準の統計を目的としない。

## 経路

```text
ホスト: ランチャー・録画・対局制御・棋譜ログ
    ├─ ネイティブ GNU Shogi 1.2p03 + 変換器
    └─ 86Box シリアル通信 ─ ゲスト中継 ─ ゲストGUI ─ やねうら王 USI
```

- GUIはゲスト内で表示し、ホスト側の指し手を通信で受ける。COM1 は既存の起動・診断経路に残し、COM2 を第一候補として双方向通信を検証する。マウス入力・画面認識による着手は使わない。
- 行単位の通信に対局ID・手数・応答確認を設け、ホストとゲストの局面、手番、持ち駒を照合する。不正手・通信断・エンジン停止・局面不一致は異常終了とし、勝敗をつけずログを保存する。
- GNU のネイティブビルドは原版と既存互換パッチを基点に作り、必要な移植差分と既存 `GNU_RESULT` / `adapterstate` 出力を識別する。既存の歴史的バイナリは旧 libc 用であり、そのまま現代ホストで起動できる前提にしない。原版・パッチ・コンパイラ・バイナリのハッシュを保存する。固定深さの手・局面・探索結果を既存版と比較し、差異を記録する。
- 既存 `historical/usi.py` の変換・局面読戻しを活用するが、現在は別VM起動専用なので、ネイティブ起動経路を追加する。10秒の既存 `movetime` / 秒読み指定を利用し、Fischer 対応は不要。
- 対局ごとに棋譜を `startpos moves 7g7f ...` 形式のテキストで保存する。評価対局では局面集の開始36手に対局で進んだ手を連結し、初手からの全手順を残す。投了や引き分けなどの結果と異常終了の理由は棋譜の指し手列に混ぜず、別の結果ログに保存する。異常終了でも確定済みの手を保存する。
- 既存GUIのAI対局は開始局面指定に未対応。評価用の36手の履歴と途中局面を表示・両エンジンに伝える機能が必要。撮影は平手初期局面から開始する。初期化中に時計を進めない。表示時計は各手の経過時間を示し、厳密な時間切れ判定には使わない。

## 強さの比較

- [互角局面集の説明](../private/gokaku/README.md) と `private/gokaku/taya36.sfen` を使う。現在のファイルは1,957行、各行 `startpos moves ...`、SHA-256 `22950f42a2d65292fa689a8c84e3af7dc160c571e9aa559699b0beaf1bc9adce`。36手の手順を合法性確認のうえ履歴ごと引き渡す。ソースの取得元・利用条件を確認し、private データ自体を公開成果物へ混ぜない。
- 開始局面を重複なく選ぶ。選択順の乱数seed・行番号・手順・データセットハッシュを記録する。各局面で先後を入れ替えて2局。目標は50局面・100正常対局程度。異常終了は記録するが勝敗・引き分けの集計から除外し、再試行や追加の局面で補う際も区別する。
- 256手で引き分け。互角局面の36手目を含む初手からの総手数として扱う。GUI・対局器・エンジン設定を一致させて境界をテストする。詰み・投了・千日手・連続王手・入玉宣言を既存ルールに従い記録する。
- 差が極端であれば、人が経過を見て早期終了できる。自動で恣意的な閾値を設けない。勝敗・引分・正常局数・異常局数と先後別の結果を示し、打ち切り理由を記録する。
- 既存 `historical/match.py` は異常終了を相手の勝ちと扱い、200msの猶予を超えると時間切れにするため、そのまま本番に使わない。

## 撮影

- 先手・後手を入れ替えた2局を平手初期局面から撮影し、面白い方を後で採用する。両方の元動画と棋譜は保持する。音声なし。起動前から録画し、86Boxの起動・GUI・対局・終局表示まで記録する。最終編集では30秒程度に早送り・テロップを入れるが、収録時間は制限しない。
- 86Boxのウィンドウ枠を含める。起動途中にサイズが複数回変わるため、初期サイズだけの固定クロップは使わない。固定したデスクトップ領域にウィンドウ全体が常に収まるよう配置する方式を第一候補とし、起動前から録画して全サイズで枠が切れないことを検証する。余白は編集時に調整できる。必要なら画面全体収録や追従方式を検討する。ウィンドウ枠の装飾・位置取得方法は実際のデスクトップで確認する。
- 既存 FFmpeg を使用候補とし、X11 / Wayland の実環境で適切な入力を選ぶ。録画停止とファイルの正常確定、フレーム欠落、空き容量を確認する。録画による86Boxの速度変化を録画あり／なしで測る。無圧縮素材や実行ログは専用の出力先に置き、既存測定を変更しない。

## 実装と検証の順序

1. **測定に干渉しない準備**: GNU原版・変換器・互角局面集・GUIと対局器を調査し、データ形式・設定・既存の制約を整理する。別出力先でホスト向けビルド・単体検証を行う場合もCPU負荷に注意する。既存測定中は86Box、負荷の大きいビルド・試験、共有イメージの更新を行わない。
2. **GNU単体**: 軽量なネイティブビルド、局面変換と `level 0 0:10` の動作、成り・打ち・終了処理・実際の経過時間を確認。原版差分を記録する。
3. **通信・GUI**: 模擬エンジンで通信、二重着手防止、開始局面と手順、256手・終局・異常停止を検証する。実ゲストの試験は測定が終わり資源が利用可能になってから行う。
4. **統合対局**: QEMU は機能診断に限定し、本番86Boxで自動対局を検証。両先後、履歴再現、保存棋譜の合法な再生、GUI表示、10秒指定、超過記録、異常終了の統計除外を確認する。強さの測定には86Boxを使う。
5. **録画**: ウィンドウのサイズ変化を含む起動から終局まで枠が切れず無音で収録されること、映像と棋譜の対応、ファイル確定を確認。2局を撮影する。
6. **評価**: 最強ビルド決定後、設定を固定して局面ペアを順に実行し、正常局100程度または人の判断で早期終了する。

## 残る実施時の判断

最強ビルド・モデルは確定時に指定する。運用タイムアウトは10秒を厳格に裁定するためではなく停止検出のために、実測後に十分長い値を定める。256手は元棋譜36手を含む総手数として実装する。途中の撮影画面に表示する選手名や動画のテロップ内容は後から決められる。
