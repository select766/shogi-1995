# GNU Shogi 対やねうら王：水匠5による調査

2026-11-08 最終集計。100局、水匠5による全100局の解析、録画2本と参考対局は完了。最新の進行状況は [対局・録画の進捗](../results/suisho5-native-gnu-live/progress.md)、集計は [水匠5による途中集計](../results/suisho5-native-gnu-live/summary.json)、先頭6局の図は [評価値の推移](../results/suisho5-native-gnu-live/evaluation-trajectories.png) を参照。原則として正常終局だけを勝敗に数える。

## 調査方法と比較の意味

GNU Shogi 1.2p03は現代Linux上、やねうら王の固定候補は86Box上のPentium 100 MHzで、定跡・先読みなし、各手10秒を指定。選んだ36手の開始手順ごとに先後を入れ替える。GNUの原版に由来する互換修正と既存の中継器、エンジン・モデルのハッシュは各シリーズのmanifestを参照。局面の合法性、手番・盤・持ち駒の読戻しを照合する。256手は開始手順を含む総手数。異常終了は勝敗から除外し、記録する。

[水匠5公式配布](https://github.com/yaneurao/YaneuraOu/releases/tag/suisho5) の `Suisho5.7z` を取得し、含まれる評価関数 `nn.bin` のSHA-256 `768068f0d534a0603a5d38bcd143de6bbca820d5f1c95a14d40863e5b7892d76` が既存のローカルコピーと一致することを確認した。解析エンジンはローカルの YaneuraOu NNUE 9.01git AVX2、バイナリSHA-256 `f42ebc776867bdb21fffb55fe15e292683eff42d508c75871ba4e76a142ad9bb`、水匠5評価関数、1スレッド、ハッシュ128MiB、定跡なし、`FV_SCALE=24`、原則1局面50万ノード。これは公式配布の**評価関数を使った別バージョンのやねうら王**であり、2021年当時の水匠5バイナリそのものではない。現代の強い別評価として有用だが、比較対象のやねうら王と探索コードの系統を共有し、完全に独立・絶対的に中立な審判ではない。

評価値はどちらの手番でもGNUから見た符号に統一。正ならGNU有利、負なら不利。評価値は勝率でも駒得そのものでもない。互角局面集は水匠作者による当時の別の選定基準で作成されたものであり、現在の水匠5でも全局面が厳密に0という保証はない。指定ノード数は探索上限で、評価値はその上限までに出力された最後の上下限表示のない反復深化結果を記録するため、各評価のノード数は上限より小さい場合がある。解析値には探索誤差、評価関数の偏り、手番や履歴の影響がある。評価値の前後差は厳密なミス点数ではない。図の線は±3000で表示を打ち切り、赤点は詰み評価で、数値評価とは別に示す。

## 探索速度の参考値

調査時点で、8秒以上を報告した探索のノード数を各エンジンの報告時間で割ったところ、前半系列はGNU 180手の中央値約106.7万ノード/秒、86Boxやねうら王179手の中央値約6750ノード/秒だった。後半系列でもそれぞれ32手の中央値は約97.2万・約7650ノード/秒。GNUはホストの1コアを使い、速度不足で単純に探索数が少ない状況ではない。ただし**両者のノードの定義、評価計算、枝刈り、探索深さは異なる**ため、1ノードの価値や棋力をこの比から推定できない。並行処理・CPU周波数・局面の違いによる変動もある。

## 最終集計：50局面・先後入替の100局

正常終局100局はすべてやねうら王勝ち、GNU 0勝、引分0、異常終了0。GNU先手50局・後手50局で、100局すべての棋譜を独立に再生し、各終局で合法手がなく王手中であることを確認した。開始局面は盤・持ち駒・手番を照合して50種類、各2局で先後が入れ替わっている。開始36手を含む総手数は46〜113手、中央値78手。対局開始後の手数は10〜77手、中央値42手。

水匠5で100局すべての開始局面を解析した結果、GNU視点の評価値は -175〜+175、中央値0だった。先後を入れ替えた同一局面を2回含む値であり、100個の独立局面ではない。解析可能な数値評価の連続区間では、GNUの1566手中618手（39.5%）、やねうら王の1598手中160手（10.0%）で、指し手側の評価が200以上低下した。別々の有限探索による差であり、詰み表示をまたぐ手は除き、独立な誤差や客観的失着率とはみなさない。

## 初期6局：開始はほぼ互角、その後GNU側が崩れる

水匠5・50万ノードによる36手目の評価は、先後入替の3組についてGNU側から見てそれぞれ `+23/-23`、`+16/-16`、`+4/-4`。開始条件だけで片方が大きく有利だったとは見えない。最初の6局は全てやねうら王勝ち。別の手番での再解析のばらつき、少数の局面による制約に注意する。

同じ水匠5で全着手前後を評価したところ、数値評価が連続した局面に限って、GNUの94手中41手でGNU側評価が200以上低下、18手で500以上低下した。やねうら王の96手では、指し手側から見た200以上の低下が12手、500以上が4手だった。探索量は固定ノードで、詰み評価を含む移行は除外。各手を同じ水匠で別々に探索した差であり、反対符号の変動や探索のばらつきも含む。局面・指し手間の独立性はないため、数値は傾向の説明であって精密な統計的検定ではない。

## 具体例を300万ノードで再確認

- **1局目**：38手目終了時、GNU先手の評価は `+105`。39手目GNUの `R*8e` 後は `-813`。続くやねうら王の `2g4i+` に対するGNUの `5h6i` 後、水匠は後手側の詰みを示した。局面ごとの有限探索による参考値であるが、評価の急落は50万・300万ノードの両方で見えた。
- **2局目**：39手目終了時、GNU後手の評価は `+197`。40手目の `B*3g` 後は `-1292`。やねうら王は次に `7g6e` と指し、水匠の候補とも一致した。開始局面そのものの不利では説明できない。
- 元の手を一度再現するだけで強さや原因は確定しない。同じ局面をGNUの新しいプロセスで10秒探索した比較では、2局目の `B*3g` ではなく `4c4d` を選んだ。そこで、実戦と同じく2つの局面を順に探索する試験を行うと `7a8b` の後に `B*3g` が再現し、各局面の前にプロセスを再起動した場合は `7a8b` の後に `4c4d` になった。各1回の観測で、表の残存に加えて実行時間・探索状態などの差が含まれる。「この手だけを特定のバグが起こした」とはまだ言えない。さらに、`TTadd` の更新を有効にし、置換表の消去バイト数を正す2か所だけを変更した検証版では、同じ2局面を連続探索しても `7a8b` の後に `4c4d` となった。しかし再度、原版相当で同じ2局面を連続探索すると、消去せずに `4c4d` となる回もあった。10秒間に探索できる量などの変動があり、この少数例だけでは残存表が悪手の原因と断定できない。検証版は置換表と評価キャッシュの消去を同時に変えており、両者の影響も未分離。別局面での比較を継続中。

## 置換表の初期化を変えた参考試験

原版相当と、各 `new` 時に置換表・評価キャッシュを確実に消去する検証版で、3局の実戦履歴に沿ってGNUの過去の思考を順に再実行した。途中で選んだ候補が実戦手と異なっても、次の局面は実戦棋譜に戻すため、直接対局ではなく局面別の診断である。10秒探索は再実行ごとに変動する。

候補が異なった5局面について、各候補を指した後を水匠5・300万ノード上限で再評価すると、消去版の評価が高いのは3局面、原版相当が高いのは2局面だった。たとえば3局目40手目終了時は原版相当 `8h9g` 後 `-422`、消去版 `P*2d` 後 `+8`。一方、同局38手目終了時は原版相当 `6g6f` 後 `-10`、消去版 `2h3h` 後 `-223`。極少数の局面であり、消去修正が棋力を改善すると断言できない。探索情報を引き継ぐこと自体は通常の対局でも行われるため、毎手消去する方式を歴史的な正常動作とみなすこともできない。比較の変更箇所は [検証用パッチ](../historical/ttclear-audit.patch)、生データは `.local/native-gnu-audit/ttclear-critical/result.json` と `.local/suisho5-analysis/ttclear-judgment.json`。

## 時間を6倍にした参考試験

上の3局面で、通常の10秒に加え、GNUを新しいプロセスから60秒探索させた。1局目では `R*8e` から `R*3e` に変わったが、その手の後の水匠5・300万ノード評価はGNU側 `-760` で、依然として不利と判定された。2局目は `4c4d`、その後の水匠評価は `+140`。3局目は `5i5h`、その後の評価は `-3334` だった。3局面だけの参考例で、追加時間の効果を一般化できない。新規プロセスのため本対局中の前手からの表の残存状態とも異なる。データは `.local/native-gnu-audit/long-think/result.json` と `.local/suisho5-analysis/long-think-comparison.json` にある。

## 原版のバグと棋力の切り分け

原版には取り返し時の探索延長を抑制してしまう型変換がある。`capture=512` を符号付き8bit変数へ代入するため、この環境では0になり、その条件が働かない。これは原版ソースにもある。後年のGNU Shogi 1.3.2についても[2010年の実装者による指摘](https://talkchess.com/viewtopic.php?t=36349)があり、[GNU公式の1.4.2原版](https://ftp.gnu.org/gnu/gnushogi/gnushogi-1.4.2.tar.gz)では同じ箇所が真偽値に変換されていることを確認した。1.4.2アーカイブのSHA-256は `1ecc48a866303c63652552b325d685e7ef5e9893244080291a61d96505d52b29`。いずれも現対局での影響量の証明ではない。

この1点だけを直した別バイナリと原版相当を同一の局面・10秒・初期化条件で比較した。上記1局目の分岐では原版 `R*8e`、修正版 `8f8g` となったが、独立に300万ノードで再探索した水匠評価はそれぞれGNU側 `-915`、`-838`。どちらも不利であり、この局面の失敗をそのバグだけで説明することはできない。3局目の別の局面でも両版の手は変化したが、どちらも水匠評価は大きく不利だった。各局面1回・少数例で、修正版全体の棋力差を測ったものではない。

GNUは探索・評価・定跡を手作業で構成した1995年の実装であり、対戦相手は現代の学習済み評価関数と探索を1995年相当機に移植したもの。局面評価や探索の技術差が主要因である可能性は高いが、現在の証拠だけで各要素の寄与率は決められない。バグ、局面再構築と内部置換表、コンパイラ、ハードウェアの違いもある。したがって結論は **「開始局面の偏りだけではなく、対局中の選択手に大きな差が見える。単一の偶発バグだけが原因とは示されていない」** までとする。

詳細な原版・32/64bit・時間設定・ハッシュに関する調査は [ネイティブGNU Shogiの動作調査](native-gnu-strength-audit.md)。300万ノードの結果は `.local/suisho5-analysis/pass-deep-001/analysis.json` と `.local/suisho5-analysis/critical-compare.json`、50万ノードの全手データは `.local/suisho5-analysis/live/combined.json`。中継器は毎手局面を再構築し、原版の置換表はビルド条件により前手の内容が残り得るので、再現性の限界として扱う。

## 追加の対照対局

取り返し修正版と原版相当の直接対局は、同じ3開始局面・先後入替の6局で、修正版5勝・原版1勝だった。修正版と86Boxやねうら王の同じ3局面・先後入替6局は、やねうら王6勝・修正版0勝だった。いずれも少数局の参考試験であり、本番の原版100局には混ぜない。修正が原版間の対局に影響する可能性はあるが、現代エンジンとの大差を解消する証拠にはならない。

## 実行状況と撮影

手順の重複しない50行を前半25行・後半25行に分け、それぞれ先後入替2局ずつ実行する。ただし36手目の盤面・持駒・手番を照合すると3組に同一局面があったため、重複側の3組6局は独立開始局面の集計から除き、別の3局面6局を録画後に補充する。対象行と補充行は `.local/native-gnu-evaluation-supplement.json` に記録する。複数の86Box、録画、解析を同時実行しているためCPU競合が生じ得る。秒読みは厳密な時間切れを課さず、各手の時間・ノード数を保存する。前半ワーカーを50局で止める予定だったが実際には100局まで完走した。その後半50局は後半ワーカーと同じ開始手順なので本集計から除外した。さらに同一開始盤面3組の重複側6局を除外し、別の3局面6局を補充した。生データの対局は合計156局、採用は50局面×先後入替の100局。完了前の対局・異常対局は集計から除く。

86Boxの枠を含む専用X画面で、平手からの対局を先後入替で2本撮影する。映像は無音MKV・H.264、盤・棋譜は実ゲストGUIに表示し、指し手は自動入力。録画用の処理は別CPUに割り当てるが、ホスト全体の競合を完全に排除したわけではない。生動画・棋譜・ログは `.local/match-video/recording-gnu-sente-02/` と `.local/match-video/recording-gnu-gote-02/` に置く。先後入替の短い結合試験では各2手の自動着手と画面枠の記録を確認済み。先手GNUの本番は64手・後手やねうら王の詰み、後手GNUの本番は39手・先手やねうら王の詰みで終局し、両方の映像・棋譜・ゲストの10秒指定を独立検証した。各 `result.json` と `verification.json` に結果を記録する。30秒の編集版はまだ作っていない。
