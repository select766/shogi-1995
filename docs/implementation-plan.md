# 1995年環境へのやねうら王移植計画

2026年11月6日時点のレビュー案。最優先は11月8日18時00分JSTまでの対局成立であり、初版は駒得評価で構築する。NNUEと学習は、その後の改善候補とする。環境構築、ビルド、エンジン実行、学習、外部棋譜の取得は本計画作成の範囲では実施していない。

## 推奨構成

| 項目 | 第一候補 | 選定理由と条件 |
| --- | --- | --- |
| ホスト | 既存Ubuntu x64 | 確認できたCPUはRyzen 7 5700X。エミュレーション速度は実測で判定する |
| 性能再現 | 86Box安定版 | 旧PCのCPUと周辺機器を再現。採用時に版と設定を固定する |
| 仮想PC | Pentium 100 MHz、RAM 32 MiB、IDE HDD 504 MiB程度、VGA、16550A | 1995年のPC互換機を想定した提案値。対応マザーボードとBIOSは起動検証で確定する |
| ゲスト | Slackware 3.0、Linux 1.2.13を第一候補 | 1995年のELF移行期の環境。実際の媒体、カーネル、パッケージを照合する |
| 移植元 | 上流やねうら王の通常探索と駒得評価 | 学習済みモデルへの依存を避け、まず移植と対局接続を検証する |
| コンパイラ | ホスト側GCCの32bit Pentium向けビルド | 命令制約と旧OS用ランタイムの適合を別々に検証する |
| USI中継 | Bash起動スクリプトとPython 3標準ライブラリ | プロセス管理、非同期中継、期限監視、ログを実装する |
| ゲストとの接続 | 86Boxの仮想シリアル接続 | 初版ではゲストのネットワークやSSHを不要にする |
| 対局UI | ShogiHome | CLIのパスをUSIエンジンとして登録する |
| 自動評価 | PythonのUSI対局ハーネス | 既存train-nnueの処理を調査して再利用し、棋譜、裁定、時間、構成情報を保存する |

CPUとRAMはレビュー時の提案であり、確定要件ではない。MMX、SSE、SSE2、CMOVなどPentium 100にない命令は使用しない。RAM不足を理由に黙ってメモリを増やさず、初版は駒得評価と小さな置換表で収める。

86Boxの公式説明にはPentiumまでの再現とLinux対応があり、ホスト単一コア性能が実行速度に影響するとされている。[86Box公式](https://86box.net/)

### CUI構成とGUI構成

Slackware 3.0にはXFree86によるX Window環境とFVWMが含まれ、GUIを利用できる。導入したパッケージと起動するサービスを分けて管理する。[Slackware 3.0の配布アーカイブ](https://slackware.uk/slackware/slackware-3.0/disk1/contents/)

| 構成 | ゲスト | 操作画面 | 用途と優先度 |
| --- | --- | --- | --- |
| CUI | Xを起動せず、エンジンと必要最小限のサービスを実行 | USI対局ハーネス、必要に応じてホストのShogiHome | 性能測定と大会の標準構成。11月8日の対象 |
| ホストGUIで対局 | CUI構成と同じ | ホストのShogiHomeに将棋盤を表示 | 人間との対局を早期に実現。エンジンの計算はゲスト内 |
| ゲストGUIで対局 | XFree86とFVWM、将棋盤アプリを実行 | エミュレータ内の当時のデスクトップに盤面を表示 | 将来の展示向け拡張。11月8日の必須条件にはしない |

CUI構成はゲストのCPUとRAMを探索に回すための基本とする。GUIを止めることで得られる改善量は実測し、最速であることを未測定の段階で断定しない。エミュレータ自身のホスト側ウィンドウの有無と、ゲストでXを動かすかどうかは別の設定として扱う。

ゲストGUI構成は、共通のCUIイメージを複製し、X関連パッケージを追加する。CPU、RAM、エンジン、モデルは共通にし、GUIの有無による性能差とメモリ余裕を比較する。GUIのためにRAMを増やす場合は別のハードウェア構成として記録する。XFree86で扱える仮想ビデオカードとマウスを選び、シリアルマウスを使う場合はUSI通信のCOMポートと分離する。

Xが起動するだけでは将棋の対局画面は得られない。ゲスト用の将棋盤アプリは別途選定し、当時のXlib等で動く最小GUIの作成も候補とする。現代のShogiHomeを旧Linux上で動かせるとは想定しない。ゲスト用GUIはUSI経由で同じエンジンを子プロセスとして起動し、盤面、持ち駒、成り、先後選択、投了、対局終了を扱う。ホストUSI接続との同時利用は避ける。

実装順はCUIで対局成立、ホストGUIで人間との対局、ゲストGUIの展示構成とする。将来の完了条件は、ゲスト内でGUIを起動し、人間の指し手入力からエンジンの応手表示までを含めて一局完走できること。GUI有効時のNPS、常駐メモリ、スワップ、停止応答時間をCUI構成と比較する。

### 代替ツールの位置付け

| 候補 | 本企画での位置付け |
| --- | --- |
| QEMU TCG | OS起動、32bitバイナリ、通信の切り分け用。性能測定の主系にはしない |
| KVMや一般的な仮想マシン | 当時の速度を再現する用途には採用しない |
| BochsやPCem | 86Boxで成立しない場合の再調査候補。期限直前に並行整備しない |

QEMUの`icount`は実行命令数を仮想時間に対応付ける仕組みで、特定CPUの命令所要時間を再現する機能ではない。CPU名や命令数の制限だけでPentium 100相当とは扱わない。[QEMU公式資料](https://www.qemu.org/docs/master/devel/tcg-icount.html)

## 最初に解決する移植上の問題

### CPU命令と32bitへの対応

上流Makefileでは`NO_SSE`の分岐に`-m32 -march=pentium3`が含まれる。`NO_SSE`を指定するだけでは対象CPUを満たさないため、専用ターゲットを追加する。[上流Makefile](https://github.com/yaneurao/YaneuraOu/blob/master/source/Makefile)

候補フラグは`-m32 -march=pentium -mtune=pentium -mno-mmx -mno-sse -mno-sse2`とする。自動生成する命令、リンクするライブラリ、起動コードも対象に含める。`readelf`と`objdump`による確認に加え、対象CPU設定での実行を必須とする。

64bit整数演算は複数の32bit命令で実装できるが、組込み関数、128bit演算、アラインメント、アトミック演算、メモリ使用量に32bit依存の問題がないか確認する。

### 1995年Linuxと現代C++の互換性

本計画で最も不確実性が高い部分。Ubuntuで`-m32 -static`を指定しても、古いカーネルとの互換性は保証されない。静的リンクでも、ライブラリが要求するシステムコールやスレッド機能は残る。

最初の技術検証では、次の順に進める。

1. Slackware媒体のELF形式とlibc5系ABIを調べる。Cの最小プログラムで起動、入出力、時刻取得、メモリ確保を確認する。
2. ホスト側GCCでゲスト用sysrootを使う構成を試す。現代C++の構文対応と、リンク可能なlibstdc++等の実行時ライブラリを区別する。古いlibstdc++を現代C++にそのまま流用できるとは想定しない。
3. エンジンが必要とする標準ライブラリ機能を列挙し、旧OSで使える部分と置換対象を決める。必要なら起動、入出力、時刻、アライン確保などを限定した互換層で置換する。C++標準ライブラリ全体の自作には進まない。
4. `Threads=1`だけでOSスレッドが消えるとは考えず、探索を単一実行経路にする専用バックエンドを検討する。NUMA、巨大ページ、不要なファイル操作や学習機能は初版から外す。
5. 同期探索中にも入力をポーリングし、`stop`と`quit`を処理する。単にスレッドを削除してUSI入力を止める実装にはしない。

11月6日夜までにC++の最小実行と駒得エンジンへの移植経路が示せなければ、高リスクと判定する。依存が少ない旧版やねうら王を調査し、変更量で選び直す。その場合も「2026年版の移植」とは表示せず、採用年とコミットを明記する。

旧OS対応が成立しない場合、現代Linuxを入れて本要件を満たしたことにはしない。「1995年CPUと現代OS」の別実験への変更はユーザーレビュー事項とする。現時点で11月8日の達成は保証できず、この技術検証が工程の成立条件となる。

## USI中継と対局時の動作

```text
ShogiHome または対局ハーネス
    ⇅ stdin と stdout
run-shogi-1995.sh → ホスト側ブリッジ
    ⇅ 採用版で確認したローカル接続
86Boxのシリアルデバイス → ゲストの /dev/ttyS0
    ⇅ raw入出力
ゲストの起動ランチャー → 移植したやねうら王
```

86BoxにはLinuxホスト向けの仮想コンソールおよびnamed pipeによるシリアル接続に関する実装がある。採用版で接続APIとデバイス名を確認し、まず双方向エコー試験を行う。接続先をUnixソケットと仮定してコードを書き始めない。[86Box公式リリース情報](https://86box.net/2026/05/17/86box-v6-0-beta.html)

- 外部の入口は`./run-shogi-1995.sh`に固定し、作業ディレクトリに依存させない。
- 初版は1エンジンにつき1台のVM。二重起動をロックで検出し、自動評価は逐次実行する。
- 通常はラッパーがVMを起動して準備完了を待つ。GUIの待ち時間が不足する場合は、同じスクリプトの`--prepare`で事前起動し、通常起動で専有接続する運用を用意する。
- 起動ログとシェルプロンプトはUSI回線と分離する。ttyをraw、echoなしに設定し、改行とバッファリングを統一する。エンジン出力は逐次flushする。
- stdoutはUSI専用。ログはstderrかファイルへ出す。探索や評価をホストへ代行させない。
- `usi`、`isready`、`setoption`、`usinewgame`、`position`、`go`、`stop`、`gameover`、`quit`を扱う。`go infinite`も停止できるようにする。
- `Threads`は1固定、`USI_Hash`は仮に1〜4 MiB。上限超過を黙って受け入れない。Ponderはfalseのみ公開し、ponder対応は改善工程へ回す。
- シリアルは115200 bpsを候補とする。大量の`info`で探索を止めないよう出力頻度を抑える。`bestmove`や制御コマンドを滞留させず、長い`position ... moves ...`を切らない。
- 読み書きを同時処理し、EOF、異常終了、起動失敗を検出する。失敗時は終了コードとログを残し、架空の`usiok`や指し手を生成しない。
- 切断時は対局失敗として記録する。対局中の自動再起動は行わず、終了時は所有プロセスを回収し、次局の接続を再初期化する。

### 持ち時間

大会の時計はホストの実時間を基準にする。ゲストの時刻取得と実時間との差を検証し、`go btime wtime byoyomi`およびincrement形式の対応範囲を明記する。

ブリッジは通信遅延と時計差に備え、実時間の期限より前に`stop`を送る。余裕時間は暫定200 msから始め、短時間対局の実測で調整する。ゲストが停止を処理し`bestmove`を返すまでの時間も含めて検証する。期限超過時にホストが指し手を選ぶ処理は追加しない。

## 評価関数と既存学習資産

### 初版と改善順序

初版は`YANEURAOU_ENGINE_MATERIAL`の基本的な駒得評価を候補とする。定跡なし、1探索系統、小容量Hashで最後まで指せる状態にする。駒得版の強さをNNUE移植の結果として扱わない。

11月8日の対局可能版を保存した後、次の順に比較する。

1. 駒価値、軽量な位置評価、時間管理、32bit演算の改善。
2. 上流の標準NNUE実装を参考に、RAMに収まる小型NNUEを設計する。指定された通常の学習用棋譜から本企画で新規に学習し、train-nnueのモデルを初期重みや蒸留教師として使わない。
3. 同じ新規モデルを使ってホスト版とゲストのscalar版の評価値一致と速度を調べる。モデル形式とエンジン実装を対で変更し、整数化後の一致を確認する。

モデルの小型化は特徴量テーブル、探索スタック、置換表を含む総メモリで判断する。32 MiBのゲストRAM内で動作することを目標とし、スワップによる対局速度の確保は前提にしない。

### 利用する資産と再現手順

2026年11月6日のユーザー方針として、train-nnueは棋譜処理と対局の方法を参考にする範囲に限定する。同プロジェクトの特殊な学習実験に由来する加工データ、学習済みモデル、checkpoint、実験由来の評価データは使用しない。初期重み、蒸留教師、対戦相手への転用も行わない。

利用する学習用棋譜は、次のユーザー指定ディレクトリとする。ユーザーによればHugging Faceから取得した通常の学習用棋譜であり、利用を了承済み。

```text
/media/select766/HDCZ-UT/s7ubuntu/dev/train-nnue/dataset/tanuki-.nnue-pytorch-2024-07-30.1/
```

実装時に元データの取得元URL、公開リビジョン（確認できる場合）、利用条件、ファイル一覧とSHA-256を記録する。既存の実験用splitや加工済みデータを流用せず、この入力から本企画専用の処理を行う。処理コードの版、引数、乱数seed、訓練・検証・最終評価の分割規則と出力ハッシュを保存し、同じ入力から再生成できるようにする。モデル選抜用データと最終評価は分離する。

既存コードを参考にする場合も、実験固有の変換や依存関係が混入しないよう確認する。既存プロジェクト内で作業する場合はそのAGENTS.mdと実行ラッパーの指示に従う。元のデータや設定を変更せず、新規成果物は本企画側へ保存する。学習前に投入データ、モデル規模、計算予算、打切り条件を固定する。

外部棋譜の追加取得は今回不要とする。必要になった際に取得元、対象、容量、利用条件、用途を提示して承認を得る。

### 必須検証

- 同じソースのホスト版とゲスト版で、合法手、局面更新、詰み、千日手と連続王手の裁定を照合する。入玉宣言は大会規定に合わせる。
- startposとsfen、長い指し手列、USIオプションの境界値を検証する。
- 探索中のstop、quit、stdinのEOF、VM異常終了、連続起動を検証する。go infiniteを外部から確実に止める。
- 一定nodesでホスト版との差を調べる。時刻依存部分を分離し、指し手の完全一致だけを正しさの条件にはしない。
- 一定時間でNPS、深さ、ゲスト時間、ホスト実時間、常駐メモリ、スワップを記録する。
- 探索中に86Boxの速度表示とゲスト時計の実時間比を確認する。目標は100%維持、時計比の暫定許容差は±2%。継続的に遅延する構成は測定に採用しない。

86Boxを実機の全タイミングを保証する測定器として扱わない。結果は「固定した86Box構成上での性能」として公開し、実機未検証と明記する。測定中は重い処理や複数VMの対局を行わない。

### 棋力の測定

同じ持ち時間、先後を入れ替えた開始局面、定跡条件で比較する。まず駒得基準版対改善版、次に本企画で新規学習したモデルを使うホスト版などの参照相手を使う。開始局面も指定された棋譜から本企画の手順で作成し、学習用との分離を記録する。train-nnueの学習成果物は対戦相手にも使用しない。固定nodes比較は実装診断、同実時間比較を本企画の主結果とする。

20局は動作確認用であり、棋力推定には少ない。時間が許せば100局以上の先後ペア対局を行い、勝敗、引き分け、反則、切断、時間切れを別々に報告する。Elo換算は区間推定を添え、全勝や全敗から有限のElo差を断定しない。1995年当時のソフトに勝ったという主張には、別途そのソフトとの対局が必要になる。

## ファイル配置と来歴

実装時の配置案。大容量ファイルはGitへ追加せず、設定と来歴を管理する。

```text
run-shogi-1995.sh       USIの入口
src/bridge/            ホスト側中継と監視
src/compat/            旧Linux互換層
vendor/YaneuraOu/      固定した上流ソースとライセンス
config/86box/          マシン設定
scripts/               ビルド、転送、検証
tests/                 USIと移植部分の検証
docs/upstream.md       上流コミットと変更方針
docs/runtime.md        起動、復旧、大会当日の手順
manifests/             ソース、媒体、バイナリ、モデルの来歴
```

大容量保存先`/media/select766/HDCZ-UT/s7ubuntu/dev/shogi-1995`に`images/`、`datasets/`、`models/`、`results/`を配置する。外部ディスク未マウント時は同名ディレクトリへ誤って書き込まずエラーとする。運用用VMイメージをホストのローカルディスクに配置する案は空き容量を確認して決める。

やねうら王のソース一式は今回取り込んでいない。レビュー後に上流の候補コミットを選び、完全なSHA、取得日、URL、ソースのハッシュ、コピー範囲を記録する。既存train-nnueの作業ツリーを無条件にコピーせず、来歴を固定した上流を優先し、改造箇所を差分で追える状態にする。

配布物には採用コミットのライセンスと必要なソースを含める。BIOS ROMはLinuxと別の利用条件を持つため、入手元と再配布可否を個別に確認する。媒体、ROM、モデルは利用条件を確認するまでGitへ含めない。

測定ごとに、ホスト情報、エミュレータ版と設定、ゲストOSとカーネル、ソースSHAと差分、ツールチェーン、フラグ、バイナリとモデルのSHA-256、USI設定、対局条件、棋譜、実時間ログを紐付ける。

## レビュー時の判断事項

1. 対象PCをPentium 100 MHz、RAM 32 MiBとし、Slackware 3.0を第一候補としてよいか。
2. 11月8日は駒得評価の対局可能版を最低到達点とし、NNUEは11月13日までの改善候補としてよいか。
3. 旧OS対応が期限内に成立しない場合、旧版やねうら王への変更を許容するか。現代OSへの変更は別実験として再レビューする。
4. 電竜戦の参加形態、接続方法、持ち時間、申込内容を確定できるか。USI対応だけで大会接続が完了するとは想定しない。

レビュー後は工程1と2から着手し、ランタイム互換性と通信の成立を最初の判断材料とする。
