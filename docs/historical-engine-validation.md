# 1995年版 GNU Shogi の選定・検証とUSI接続

初回検証日: 2026-11-07。以下の実測は移行前の独立クローンで行った。移行後は本体リポジトリの `historical/` を比較対象として利用する。元研究リポジトリの変更中ファイル・モデル・VM・測定履歴は編集せず、コミット `45dcb0b6ff51fec4cd41f0156477d27ea53a3ea8` の独立クローンで実施した。ビルドは1ジョブ・低優先度、VMディスクとシリアル、Xサーバーは独立。

## 選定

**GNU Shogi 1.2p03（1995年5月）を採用する。** 無償で合法的に入手でき、年代を一次資料とソースで確認でき、当時の探索・手作業の評価関数・定跡が残ることを優先した。1995年当時の最強ソフト、または当時の全技術の代表という意味ではない。

- [GNU公式の配布案内](https://www.gnu.org/software/gnushogi/) と [原版アーカイブ](https://ftp.gnu.org/gnu/gnushogi/gnushogi-1.2p03.tar.gz)。SHA-256: `3e30ef3457dc676f58868a3078dc6ab6e6f5c7058eccd87b14a813fcc000c6b3`。
- [GNU's Bulletin 1(20)](https://www.gnu.org/bulletins/bull20.html) の1995年12月Source CD収録表に Shogi 1.2p03 がある。配布アーカイブの `doc/CHANGES` は1995年5月のp03修正と、1994年の評価・指し手生成更新を記載する。
- GNU Shogi 1.4.xは後年の修正を含むため年代固定には不採用。Bonanza以降の学習型エンジンや現代エンジンの弱設定も1995年の実装にはならない。商用の金沢将棋・森田将棋等の当時版について、正当な無償配布と再現可能なソースを今回確認できなかったため採用しない。
- ソースでは反復深化、αβ探索、null move、history、置換表、駒価値、玉との距離、利き、囲い・攻撃形のパターン、手筋のボーナス等が確認できる。定跡原本も保存したが比較では定跡なし・先読みなしに固定。
- 原版の著作権表示と `doc/COPYING` を保存。現行GNU公式ページのライセンス表記を古い配布物にそのまま当てはめず、古いソース自身のライセンス表示に従う。

## ビルド

| 比較版 | コンパイラ | 主な設定 | 実行環境 |
|---|---|---|---|
| 歴史的基準 | Slackware 3.0のGCC 2.7.0 | `-O2 -funroll-loops -m486` | Linux 1.2.13、libc 5.0.9、32bit |
| コンパイラ比較 | Ubuntu GCC 11.4.0 | `-O2 -funroll-loops -m32 -march=i486 -mtune=i486` | 同上 |

現代版も1995年のヘッダーでコンパイルし、**両版とも旧GCCのドライバ・旧binutils・同じlibcでリンク**した。現代版はGNU89、common、GNU89 inlineを明示し、PIEとstack protectorを無効化。`-m486`は当時のGCCにある選択肢で、両方の命令・チューニング対象を揃えた。最適化オプションの意味が世代間で完全に同じになるわけではない。

`historical/toolchain-packages/manifest.json` に取得URL・容量・SHA-256、`historical/manifest-{old,modern}.json` にバイナリ・ディスク・カーネル・ラッパーの識別情報を保存。`historical/build-modern-objects.sh` でホストの現代版オブジェクトを作り、独立ゲスト内で旧版ビルドと両版リンクを再実行する。既存研究のビルドスクリプトは起動しない。

原版との差分は `historical/compatibility.patch`。

1. `genmove.c` のstatic変数 `INCscore` を改名。ヘッダーのextern宣言との衝突だけを解消し、構造体メンバーは変えない。
2. `dspcom.c` に `time.h`。宣言不足による64bitホスト版の終了時クラッシュを修正。
3. 標準出力のバッファを無効化し、探索後の `GNU_RESULT`（指し手・centisecond時間・nodes・depth）を出力。
4. `adapterstate` は盤面・手番・持ち駒・履歴長の読取り専用出力。探索・評価式・時間判定式は変更しない。

最初に作った64bitホスト版は動作診断用。歴史的基準として使うのはGCC 2.7.0の32bit版。

## USI対応範囲

`historical/usi.py` がホストでUSIを受け、独立したQEMUまたは86BoxのGNU Shogiへ中継する。デフォルトは86Boxと旧GCC。Python依存はリポジトリと同じ `cshogi`。

- `position startpos [moves ...]`、`position sfen ... [moves ...]`。成り、持ち駒、先後を扱う。
- 基点を `edit` で設定し、履歴を `force` で1手ずつ渡す。`7g7f 3c3d` を最終SFENだけに変換する方式ではない。
- 毎回、GNU側から読み戻した盤面・手番・持ち駒をcshogiの局面と照合。入力の反則手や変換不一致は異常終了として検出し、適当な合法手で置き換えない。
- `isready` はGNUプロセスを再起動し、局面評価の置換表・履歴を初期化する。VM起動と初期化は `readyok` 前に完了する。
- `go btime 0 wtime 0 byoyomi 2000`、`go movetime 2000`、診断用 `go depth 2..29`、`go infinite` と明示的 `stop`。
- `stop` は旧GCCで作った `relay.c` からGNUプロセスへSIGINTを送信する。通常の2秒指定でホストが勝手にstopすることはない。
- 持ち時間消費・Fischer増分・ponder・nodes指定は未対応。非整数秒や未対応コマンド・設定はエラーにして、違う条件で黙って実行しない。
- 既存評価器が要求する固定オプションを受け付ける。`USI_Hash=2` は接続互換用であり、GNU内部の歴史的な固定テーブルを2 MiBに変更したという意味ではない。Threads=1、MultiPV=1、定跡なし、ponderなし。入玉宣言・千日手・最大手数の裁定はホスト対局器の担当。GNUの探索に現代の入玉規則を移植してはいない。

## 2秒指定と時間超過

起動引数の `2` は `InitMain/NewGame/Initialize` の初期化により15秒へ上書きされる。**起動後に `level 0 0:02` を送る必要がある。** USIラッパーは毎探索でこれを設定する。

このコマンドは `TCflag=false`, `MaxResponseTime=200`（1単位10 ms）、`ResponseTime=MaxResponseTime`, `TCleft=0`。時間制御用の余裕・延長量を計算する持ち時間モードを通らない。1秒を差し引く `onemove` 分岐も通らない。通信マージンを差し引く処理はラッパーにもない。

ただし標準設定は `ZNODES=1000`。`search.c` の終了判定は `Sdepth > MINDEPTH`、`MINDEPTH=2` も要求する。従って2秒は厳密な実時間上限ではない。VMの遅れ、1000ノード単位の確認、最低深さ、出力、局面設定・読戻し・シリアル通信がホスト時間に影響する。`info time` はGNU内部のcentisecondをmsへ変換した値で、ホスト経過時間の偽装ではない。

既存評価器の「go送信〜bestmove受信」「200 msを超えた超過は不一致」のルールはそのまま使う。超過局面を除外したり、指定を1秒へ減らしたりはしない。厳密な2秒終了を必要とする本番比較には、歴史的版をそのまま測るか、時間確認間隔だけを変更した別バリアントを採用するかという条件決定が必要。後者は今回の歴史的基準バイナリには混ぜていない。

特殊な駒数の少ない局面 `4k4/9/9/9/9/9/9/9/4K4 b RBGSNLP 1` では、86Boxの旧GCC版が2秒指定でも30秒以内に応答しなかった。タイムアウトと明示stopを記録した。これは入力を密かに除外してよい理由ではなく、最低深さ・時間チェックの限界を示す。通常局面の検証とは別に `historical/evidence/synthetic-position-limitation.json` に残している。

## 既存評価・対局の利用

`historical/evaluate.py` は既存の `scripts/evaluate-accuracy.py` を呼び出す。採点・合法手判定・時間超過判定・統計は既存のまま。共通評価器に既定では無効な `--no-history` を追加し、実験中の結果を研究用履歴へ自動登録しない。

```bash
PY="$PWD/.local/venv/bin/python"
# 本体リポジトリのルートで実行する
"$PY" historical/evaluate.py \
  --dataset .local/evaluation-data-repro/quick.jsonl \
  --output historical/results/gnu-old-quick-86box.json --backend 86box --compiler old
# 現代GCC版は --compiler modern と別の出力ファイルを指定
```

開発中エンジンの既存結果と比較する際は同じdataset SHA、backend、CPU設定、時間指定を確認する。test集合は今回読まず、開発用quickの先頭だけを接続試験に使った。QEMU結果を86Box結果と棋力比較しない。

`historical/match.py` は任意の2つのUSIコマンド（JSON配列）を受け付ける。デフォルトで `7g7f 3c3d` 後から先後を入れ替えた2局を実行。`--start-sfen` で基点、`--opening` で開始手順も変更できる。`--a-options/--b-options` はモデル固有オプション用。通常は1手2秒、ホスト側の超過許容は明示的な `--grace-ms 200`。この200msをエンジンの指定時間から差し引かない。既存のRefereeで合法手・千日手・連続王手・入玉宣言・最大手数を裁定する。

研究エンジンは凍結した `--image` と**独立した `--run-dir`**を指定して接続すること。最新候補を暗黙に選択しない。コマンド例と自動生成用の補助スクリプトは `historical/README.md` を参照。

単一の決定的な開始局面の同一条件反復は独立な標本にならない。`7g7f 3c3d` は希望した開始局面の動作確認に使えるが、安定した勝率・Elo推定には複数の開始局面を固定し、先後を対にして比較する必要がある。今回の短手数試験を棋力差やEloとして扱わない。

## 最終ラッパーの実測

通常設定の86Box / Pentium 100 MHz / RAM 32 MiB。各版で平手、`7g7f 3c3d`後、`7g7f`後、持ち駒ありの中盤SFENの4局面を検証。全応答がcshogiで合法、設定局面の読戻し照合も成功。

| 指標 | GCC 2.7.0 | GCC 11.4.0 |
|---|---:|---:|
| 2秒指定4局面のGNU報告時間 | 2.210〜2.390秒 | 2.010〜2.220秒 |
| 同じ4局面のホスト経過時間 | 2.429〜2.621秒 | 2.248〜2.434秒 |
| 既存の2200ms閾値超過 | 4/4 | 4/4 |
| `7g7f 3c3d`後・深さ4、2回のGNU時間 | 7.390 / 7.400秒 | 5.100 / 5.090秒 |
| 同探索のノード数 | 11405 / 11405 | 11384 / 11384 |
| 同探索の指し手 | 6g6f / 6g6f | 6g6f / 6g6f |

固定深さの平均時間比は旧/現代で約1.45倍（現代版の所要時間は約31%短い）。**1開始局面の2回測定に限った観測**であり、棋力差や全局面の速度比ではない。ノード数も21違うので、コンパイラを替えても完全に同一の探索木になるとは主張しない。固定深さ試験は毎回 `isready` でプロセスを再起動している。生ログ・stop応答時間は `historical/evidence/usi-86box.json` と各プロトコルログ、集約は `summary.json`。

QEMU上の2秒指定は通常4局面で約2.08〜2.13秒（初期化・通信込み）。この短さをPentium上の結果と取り違えない。QEMUの4局面の正解率評価接続試験では2/4一致、時間超過0、完走。短い試験であり、本番の正解率・棋力推定ではない。結果は `accuracy-qemu-smoke.json`。直接対決器は旧/現代GNUの先後入替2局を各12手で打切り、全24手合法で完走した（最大手数引分）。

明示stopの送信からbestmoveまでの86Box実測は旧GCC版約2.065秒、現代版約1.329秒。SIGINTを受けても探索側が時間・中断フラグを確認するまで戻らないため、低遅延stopの保証はない。通常評価に自動stopを追加して見かけの時間を合わせることはしていない。

凍結済み研究エンジン `halfkp-fixed-w8-h0-128m-radix-v1-usi`（engine SHA `700996f5cb97d0f389a693be6bea7d3814668d3609588d8baebaa39a4406d656`）との接続も、QEMU・深さ2・開始手順 `7g7f 3c3d`・先後入替2局・各8手で検証し、全16手合法で完走した。双方のVMは独立したコピー/スナップショットを使った。結果は `historical/evidence/vs-frozen-radix-qemu-smoke.json`。最大手数打切りなので「互角」の証拠ではない。

最終32bit版の自己対局もQEMUで確認した。旧/現代GCCとも136手で終局し、各136手すべて合法、駒打ち35回・成り13回を含む。旧版で最終詰み手だけ通常の `My move is` 表示が省略されることも確認し、ラッパーは常に出る `GNU_RESULT` を読むようにしている。生データは `compiler-comparison.json`。通常手以外の終局表示を指し手欠落と取り違えない。

## 本体リポジトリへの移行

ユーザーの指示により `historical/` とこの文書を本体へ移行した。GNU Shogiは研究エンジンとは別の比較対象とする。未コミットの研究測定履歴には手を加えず、旧クローン `.local/historical-1995/repo` はバックアップとして残している。

展開済み状態への依存を除き、`bash historical/setup.sh` でハッシュ固定アーカイブから両コンパイラ版を再構築できる。`--offline` は取得済みアーカイブだけを使う。ビルドの工夫、必要ツール、生成物とGit管理対象、利用方法は [historical/README.md](../historical/README.md) に記載した。旧ツールチェーンはゲスト内だけで実行し、研究エンジンやホストのシステムライブラリを置き換えない。

初回検証の少量のJSON証跡は `historical/evidence/` に保存する（取得時点のパス・ハッシュをそのまま保持）。今回以降の結果や生成manifestはGit管理外の `historical/results/` 等に保存する。大規模な正解率・棋力比較は未実施。

移行時には展開済みソース・旧コンパイラ・バイナリをコピーせず、固定アーカイブから `setup.sh --offline` で再構築した。GCC 2.7.0版、GCC 11.4.0版の両方が移行前のバイナリとSHA-256一致。本体のパスで両版のUSIプロトコル8ケース、既存評価器で2局面、凍結済み研究エンジンとの先後入替2局・計8手の接続試験が成功した。これらはQEMUの動作確認で、性能・棋力の再測定ではない。[移行検証の証跡](../historical/evidence/migration-verification.json)に構築条件と結果を保存した。
