## 固定シードでのランダム抽出

seedは`20261106`、系列名は`floodgate-hcpe-1995-v1`とする。

1. 原本を元インデックス順に復号し、局面と収録された`bestMove16`の合法性を検証する。壊れたレコードや通常の合法手でない指し手を除外し、理由を保存する。合法手数や評価値による追加の難易度選別は行わない。
2. 盤面・手番・持ち駒を同一性キーとし、手数はキーから除く。同一局面が複数回現れる場合は、最小の元インデックスを代表にする。収録手が異なる重複の件数も記録し、成績を見て代表手を変えない。
3. 代表レコードを元インデックス昇順に並べ、`random.Random(20261106).sample(eligible_indices, 5220)`で重複なしのランダムサンプルを作る。Pythonの版も記録する。
4. サンプル順でdevelopment 1,024件、test 4,096件、補助対局の開始局面100件に割り当てる。quickはdevelopmentの先頭256件とする。

抽出後は再抽選しない。元インデックス一覧、SFEN、USIの収録手、手番、元の評価値・勝敗、入力と出力のハッシュ、抽出コードと設定を保存する。別エンジンとの比較でも、seedから再生成するだけでなく、同じ固定JSONLとハッシュを指定する。

集合間の同一局面は排除できるが、元棋譜単位の分離や近接局面の非相関は保証できない。SFENの手数欄は便宜上1とし、実手数として扱わない。将来の学習では、これらの評価局面と同じ局面キーをたぬき学習データから除外する。候補の成績を見てサンプル数や抽出条件を変えない。

## 一致率の測り方

### 主指標

`一致率 = HCPEの収録手とbestmoveが完全一致した局面数 / 固定局面数`

成り・不成や駒打ちも区別するTop-1一致率を使う。MultiPVによる候補内一致、教師評価値のloss、固定ノード数の一致率は主指標に混ぜない。一致率はこの固定データセットの収録手への追従度であり、唯一の正解率やEloには換算しない。

最終比較は同じ局面について、駒得基準版だけが一致した件数、候補だけが一致した件数、両方一致、両方不一致を記録する。主な改善量は一致率差のパーセントポイント（pp）。例として20%から25%への変化は+5 ppとする。

### 86Box上での固定時間

対象CPU、RAM、Hashを固定し、1台のVMで逐次評価する。最終候補も実際にゲストで動作するモデルとバイナリを使う。

```text
setoption name NetworkDelay value 0
setoption name NetworkDelay2 value 0
isready → readyok
usinewgame
position sfen <固定したSFEN、手数欄は1>
go btime 0 wtime 0 byoyomi 2000
bestmove
```

主評価は通常の時間指定を用い、NetworkDelayとNetworkDelay2を0に固定する。ブリッジで独自に時間を減らしたりstopを追加したりせず、やねうら王自身が終了する。`go infinite`による時間測定は採用しない。比較対象エンジンにも同じ時間指定を送る。

評価器がgoをホストブリッジへ送信完了してからbestmoveを受信するまでをホスト実時間とし、ゲストのinfoに含まれる探索時間と比較する。初期化、局面設定、VM起動時間は別に記録する。NetworkDelay系以外の時間設定（MinimumThinkingTimeや秒単位の丸めを含む）も固定して保存する。時間指定は思考時間の上限であり、詰みや強制手などで早く応答する場合があるため、各局面の実測時間も残す。

1秒・2秒・5秒の秒読み指定とmovetime指定を、NetworkDelay両値0、2種類の局面で各3回、計18回検証した。2秒指定のホスト実時間は2.024〜2.039秒で、全18回のホスト実時間とゲスト報告時間の差は20〜37 msだった。著しい差は確認されなかったため、この通常の時間指定方式を採用する。[測定結果](../results/2026-11-06/timed-search.json)

毎局面で`isready`を送り、基準版・候補とも置換表と履歴を初期化する。現行実装がこれらをクリアすることを検証してから採用する。未登録の`Clear Hash`は使わず、局面ごとのVM再起動も行わない。warm状態で棋譜を順に評価する試験は主評価と区別する。

共通オプションはThreads=1、USI_Hash=2、USI_OwnBook=false、USI_Ponder=false、MultiPV=1、MaxMovesToDraw=512、EnteringKingRule=CSARule27。局面の履歴は主評価では渡さず、手数欄を1としたSFENから開始するため、履歴が必要な千日手などの判断は補助対局で確認する。

### エラーと再現性

反則手、VM/エンジン終了、時間超過は固定分母から削除せず不一致として数え、別件数も報告する。反則・異常終了がある候補は採用しない。主評価で指定時間を200 ms以上超過した場合は超過件数として記録し、運用条件を確認する。GUIから明示されたstopへの応答遅延も別途測る。ホスト全体の障害やエミュレーション速度低下の場合は測定不成立とし、原因と中断範囲を記録する。悪い局面だけを選んで再試行しない。

`bestmove resign`と27点法で正当な`bestmove win`は、有効なUSI応答として扱う。収録された通常手とは一致しないため一致率の分母に残して不一致とし、反則とは別に投了・宣言の件数を記録する。不正な宣言・指し手・形式は反則として数える。

2秒の実時間評価では全く同じbestmoveを毎回返すとは想定しない。候補と基準版を256局面のブロックで交互に実行し、先に実行する版もブロックごとに交代してホストの状態の偏りを抑える。現行ラッパーでは版の切り替え時にVMを再起動するため、ブロック数に応じた起動費用も記録する。切り替えのたびにモデルと設定を確認する。主評価では複数VMや重い学習との同時実行は避ける。

## 診断用の指標と採用基準

| 指標 | 役割 |
| --- | --- |
| 2秒での一致率 | 主指標。評価関数の精度と、旧CPUでの探索速度をまとめて評価 |
| 10,000 nodesでの一致率 | 探索量を揃えた診断。実nodesも記録し、上限のオーバーランを隠さない |
| NPS、深さ、完了深さ | 改善・退行の理由を調べる補助情報 |
| 空きRAM、モデル容量、swap、停止遅延 | 1995年構成で運用できるかの条件 |
| 手番、収録評価値の絶対値帯、王手中か否か | 苦手な局面を把握する層別一致率 |

比較集計では、先後、収録評価値の絶対値（0〜299・300〜999・1000以上）、王手の有無について、一致数・固定分母・Wilson区間・対応あり差も出力する。原JSONLのSHAと各局面・収録手を照合して分類する。これは原因調査用の記述集計であり、複数比較の補正や層別の採用基準にはしない。全体の固定分母と採用基準を優先する。比較する2測定はbackendと実行環境の署名も一致している必要がある。環境情報がない旧結果は、そのまま厳密比較へ投入せず出自を確認する。

固定nodesの試作比較はホストで高速に行ってよいが、同一バイナリ・モデルでゲストと指し手が一致するかを小さな固定集合で先に確認する。ホストの秒数やNPSをPentiumの結果として扱わない。候補の採否は86Box上の実時間評価で決める。

全体一致率にはWilson 95%区間、差には同じ局面を対応付けたbootstrap 95%区間を付ける。bootstrapは固定局面の対応を保って10,000回、seed固定。元棋譜IDを保持しないため棋譜単位の再標本化はできず、局面間の相関によって区間が狭く見える可能性を明記する。探索時間による揺れや同系統エンジン同士の相関まですべて含む区間とは解釈しない。

developmentでの改善が+2 pp以上なら最終候補の対象にする。予算内で僅差の候補が残る場合は、同じdevelopmentを別の固定順で一度再測定して時間依存の揺れを確認する。testに進む候補は1個に固定する。

この+2 ppの基準と最終testの基準は、固定した駒得基準版に対するもの。各改良で、その時点の最良モデルからさらに+2 ppを積み重ねる条件にはしない。改良同士の比較では現在の最良版を対照として追加効果を測り、差の区間が0をまたぐ場合は改善未確定と記録する。最終候補は、同じ条件のdevelopment成績と運用条件を満たす候補から選び、独立testを見る前に固定する。

testで+2 pp以上、かつ対応あり95%区間の下端が0を超え、反則・異常終了・著しい時間超過がないことを正式採用の基準案とする。区間が0をまたぐ場合は「改善未確定」とし、testを見ながらパラメータを調整しない。一致率が上がっても、棋力や大会での勝率が向上したと断定しない。

最終候補には基準版との補助対局も行う。まずmatchの先頭10開始局面を先後入れ替えて20局、双方3分・1手2秒加算、最大512手・入玉27点法を共通条件とする。これは異常や明らかな退行を見つける補助試験であり、僅差の棋力判定には不足する。時間が許せば100開始局面・200局まで拡張し、勝敗と区間を報告する。大会の先後で持ち時間が違う設定は、棋力差と時間差が混ざるため別の稼働試験とする。

補助対局の審判はホスト実測をmsに切り上げ、着手前の残り時間から差し引く。時間内の合法な着手が完了した後で2秒を一度加算する。今回の加算分を使って、すでに切れた残り時間を救済しない。この順序は[ShogiHomeのClock.stop / incrementTime](https://github.com/sunfish-shogi/shogihome/blob/main/src/renderer/game/clock.ts)を2026年11月6日に確認した。修正前の短い固定ノード対局は動作確認のみであり、実時間の棋力結果には含めない。

補助対局用runnerは`src/shogi1995/sessions.py`と`scripts/play-match.py`に実装済み。独立したVMディレクトリとロックで双方をPentium 100 MHz・RAM 32 MiBとして起動し、対局前に2台同時の5秒探索を3回ずつ測る。ホスト実測と要求時間、ホスト実測とゲスト時計の差をそれぞれ±2%内と確認し、満たせば対局に進む。[2台での短い動作確認](../results/2026-11-06/match-dual-vm-smoke-v1.json)は通過したが、固定ノードの検査であり、最終候補の実時間20局はまだ実施していない。時計条件を満たさない場合は実施条件を再検討し、一致率から勝率を推定して代用しない。

補助対局のJSONには勝敗・引分け・得点率、双方の反則・不正な入玉宣言・時間切れ・異常終了件数、実際の共通USIオプション、対局runner・審判・時計・集計コードのSHAを記録する。実時間の予定局数が正常に完了し、時計較正を通過して運用異常0件の場合に限り、固定相手との得点率を`400 log10(p/(1-p))`でElo差へ換算する。これはその相手・時間条件に対する参考値で、リーグのレーティングではない。動作確認用の固定ノード対局や途中結果にはEloを付けない。

不確かさは同じ開始局面の先後2局を1組として扱い、組ごとの得点率が0〜1に収まることを使ったHoeffdingの95%区間をEloへ変換する。開始局面間の独立性を仮定する保守的な区間だが、原データに対局IDがないため、異なる開始局面間の未知の相関は扱えない。全勝でも確実な無限大の棋力差とは扱わず、片側が無限大になる端点はJSONの`null`と境界ラベルで明示する。10組・20局では区間が広くなることも報告する。集計の9件の検査は通過済みで、先後の対応、引分け、全勝時の有限JSON、運用異常の敗者への帰属、途中・固定ノード結果のElo抑止を確認した。

集計と保存の接続は、2026年11月6日20:41 JSTにホスト上の固定64ノード・各4手・先後2局で確認した。反則・時間切れ・異常終了0件、`rating_eligible=false`とElo値なし、コードSHA・共通オプションの保存を確認した。[集計の短い動作確認](../results/2026-11-06/match-summary-native-smoke-v1.json)。これはPentium上の速度・棋力の測定ではなく、最終の実時間20局には数えない。

## 学習データと強化の順序

学習元は許可済みの次の原データだけを使用する。

```text
/media/select766/HDCZ-UT/s7ubuntu/dev/train-nnue/dataset/tanuki-.nnue-pytorch-2024-07-30.1/
```

今回の読み取り確認では、`.bin`は1,016ファイル、合計約320.0 GBで、全ファイルのサイズが40 bytesの整数倍だった。同梱READMEはMITライセンス、深さ9、未シャッフル、qsearch末端への置換なしと記載している。少数のレコードでもscore、PV初手、gamePly、勝敗の形式を確認した。全件の復号・合法性確認を済ませたという意味ではない。

PV初手は原棋譜の実着手とは限らないため、たぬきデータの教師手一致率とHCPEの収録手一致率を混同しない。train-nnueの加工済みデータ、モデル、checkpointは使わない。Floodgate評価局面と同一の盤面・手番・持ち駒を学習入力から除外し、照合した範囲と除外件数を記録する。学習用validationもたぬき側で別途確保し、Floodgate testの結果や正解手を学習へ戻さない。

| 順序 | 作業と比較対象 |
| --- | --- |
| 1 | 評価器、HCPEからのランダム抽出、対応あり集計を実装し、駒得基準版のquick/developmentを測る |
| 2 | 駒価値と軽量な位置評価を改善し、2秒一致率がどの程度動くか確認する |
| 3 | 原データから小型NNUEを新規学習。最初は小さな特徴量・中間層から始める |
| 4 | 量子化後の評価値、32bit・scalar推論、RAM内動作を検証し、ホスト診断と86Box評価を行う |
| 5 | developmentで候補を固定し、testと補助対局を行う |

基準エンジンは`config/evaluation/material-v1-frozen.json`に固定したソース`06219a9`の駒得版。共通ブリッジは独自の時間制御を廃止した現在の版に固定し、基準・候補とも同じ版を使う。実行ファイル、ゲストイメージ、依存物、設定を保存してから改造する。NNUEは現在の約18 MiBの空きRAMをすべて使い切る設計にせず、まずモデル10 MiB以下を目安とし、実際の総メモリと2秒一致率で判断する。

## 実行予算と成果物

主評価の純探索時間はquickが約8.5分、developmentが約34分、testが1版あたり約2.3時間。testで基準版と候補を測ると純探索だけで約4.6時間になり、256局面ごとの切り替えに伴う約32回の起動は合計約16分を追加する。初期化・通信・停止処理も別途加わるため、最初の32局面の試験で総時間を見積もり直す。補助対局の費用は別枠で記録する。予算が不足する場合は評価集合を成績から削らず、候補数と強化案を減らす。

大きなデータと評価明細は本企画用外部ディスクへ保存し、リポジトリには設定、manifest、要約、再現手順を残す。各局面についてexpected/actual、合法性、一致、不一致の理由、実時間、stop遅延、nodes、深さ、エンジンとモデルのハッシュを保存する。

レビュー対象は、HCPE入力版、固定シードとランダムサンプルの集合規模、2秒の主指標、+2 ppと区間による採用基準、および補助対局の位置付けとする。

## 実装と試作の記録（11月6日）

`extract-evaluation.py`で原本の全856,923件を検証し、同一局面を整理した840,778件から指定の5,220件を抽出した。入力異常は0件。同一局面の16,145件には収録手の異なる重複があり、最小インデックスを代表とする規則を適用した。独立した再抽出でも全出力のハッシュが一致した。固定集合と元インデックスは`manifests/evaluation-data.json`で特定できる。`verify-evaluation.py`は入力ハッシュ、元レコードとの対応、合法性、集合分離を検査する。

測定コマンドは`scripts/evaluate-accuracy.py`、対応あり比較は`scripts/compare-accuracy.py`。エンジンの起動argvをJSONで渡し、`--dataset`で固定JSONL、`--output`で新しい保存先を指定する。`--engine-id`と`--engine-sha256`は必須。`--image`付きのブリッジを指定したときはゲスト内の実行ファイルのSHAを照合する。モデル固有のオプションは`--engine-options`に指定し、共通測定条件の変更は禁止する。途中の測定も固定分母で保存し、比較コマンドは未完走の結果を拒否する。プロトコル全文、エラー、各局面の実測時間・合法性・探索情報を保存する。

たぬき原本から、別ファイル群のvalidation 32,768件とtrain 2,000,000件を新規抽出した。データは外部ディスクの`training/tanuki-blocks-v2`に保存した。HCPE/Apery形式とPSV形式ではMove16の成り・駒打ちフラグが異なるため、PSV用の復号を実装した。v2では合法性検査の失敗は0件で、評価集合との重複173件とvalidationとの重複21,892件をtrainから除外した。初期のv1抽出は形式を混同して一部の合法レコードを除外したため、学習元として使わない。

最初の試作は左右対称の駒位置・持ち駒の計637係数、1,286 bytesのモデルである。新規学習したpsqt-v2の整数評価値は、validationの256局面で32bitエンジンとPython参照計算が完全一致した。固定quickの先頭32件での86Box測定は基準12/32、試作8/32だった。試作は反則・エラー・時間超過0件だが、改善を示していないため採用しない。小標本のため性能差を確定する結果でもない。[測定明細](../results/2026-11-06/accuracy-smoke32.json)、[対応あり比較](../results/2026-11-06/accuracy-smoke32-comparison.json)。

基準のイメージは`.local/baselines/material-v1`、試作は`.local/candidates/psqt-v2`に分けて保存している。`run-shogi-1995.sh --image <root.ext2>`で候補を指定できる。既定の対局用イメージは維持し、採用基準を通った候補だけを切り替える。

基準駒得版のquick 256件は80件一致（31.25%）、反則・異常終了・時間超過0件で完走した。初期化と起動を含む総時間は約668秒、最大応答時間は2,091 msだった。[基準quickの全結果](../results/2026-11-06/material-v1-quick256.json)。これはdevelopmentの一部であり、testの結果ではない。

交互実行は`scripts/evaluate-pair.py --baseline <固定manifest> --candidate <固定manifest> --dataset <固定JSONL> --output <新規出力先>`を使用する。ブロックの順序と共通条件を固定し、完走済みブロックの再利用時も入力とバイナリ・イメージ・モデルを照合する。実際の32bit基準バイナリを使った4局面・2ブロックの動作検査、結果を再実行せずに読み直す再開検査、条件が変わった再開を拒否する検査を通した。この検査の短い時間指定は動作確認用であり主評価には含めない。

小型ネットワークtiny-v1の最初の32局面は7/32一致、基準との差は−15.625 pp（対応あり区間−34.375〜+3.125 pp）だった。反則・異常終了・時間超過は0件だが、採用できる改善はない。初期化後のゲスト空きRAMは7,467,008 bytes、swapは0。NPS中央値は3,813で、同じ32局面の基準7,161.5の約53%だった。全特徴の再加算による速度低下と、学習精度の両方を改善対象とする。[測定](../results/2026-11-06/tiny-v1-smoke32.json)。

たぬきvalidation全32,768局面で、floatモデルと整数モデルの教師lossは0.603228と0.603423だった。量子化による評価値差のRMSEは約24.7、99%点は絶対差約67.3。したがって初版の退行を整数形式の破損と判断する証拠はない。[量子化検証](../results/2026-11-06/tiny-v1-quantization.json)。

固定10,000ノード・quick 256局面のホスト診断では駒得版76件、PSQT 78件、tiny-v1 72件一致した。いずれの差も対応あり区間が0をまたぎ、精度の明確な改善はまだない。この診断のホスト秒数やNPSはPentiumの性能として使わない。同一バイナリ・モデルのゲストとの固定ノード一致も検証する。

固定10,000ノードの8局面で、tiny-v1のホストと86Boxのbestmoveおよび実ノード数がすべて一致した。[照合結果](../results/2026-11-06/tiny-v1-native-guest-nodes-parity.json)。USIのPV出力は経過時間で間引かれるため、最後に報告されたdepthはホストとゲストで一致しない場合があった。現行測定器の`depth`はこの最後の報告値であり、探索終了時の完了深さを保証する値ではない。

次の試作では、同じ原本と除外規則でtrainを16,000,000局面へ拡張した。出力は`training/tanuki-blocks-v3`、特徴量は`training/tiny-features-v2`に作成する。validation 32,768局面は変更しない。testは引き続き未使用。

1,600万局面で再学習し祖先差分更新を使うtiny-v2は、86Boxのquick 256局面で82件一致（32.03%）、基準80件との差は+0.78 ppだった。対応あり95%区間は−5.47〜+7.03 ppで、改善は未確定。反則・異常終了・時間超過0件、NPS中央値は4,681、空きRAMは7,434,240 bytes、swapは0だった。[対応あり比較](../results/2026-11-06/tiny-v2-86box-quick256-comparison.json)。各測定の日時・条件・コミット・機能差分は[測定履歴](measurement-history.md)を随時更新する。

同じtiny-v1の重みで祖先差分更新を使った32局面は9件一致、NPS中央値4,744.5だった。全再加算版の7件・3,813から速度は改善したが、一致率の差を確定する標本数ではない。testは使用していない。

左右対称・幅32の線形出力をepoch途中で選択したtiny-v7は、86Boxのquick 256局面で90件一致（35.16%）となった。基準80件との差は+3.91 pp、対応あり95%区間は−2.34〜+10.55 ppで、まだ改善は確定していない。反則・異常終了・時間超過0件、NPS中央値5,146、初期化後の空きRAM6,217,728 bytes、swap0。残る候補とのquick比較後、development全1,024件で確認する。[比較結果](../results/2026-11-06/tiny-v7-86box-quick256-comparison.json)。

長い測定のメモリ確認のため、以後は初期化直後に加えて測定終了時の`guest_memory_end`も保存する。通常のホスト実測時間には、この診断コマンドの費用を含めない。測定器・USIクライアント・ブリッジのコードSHAも保存する。ホストで固定ノード診断を行う際は、実バイナリとモデルのSHAを起動前に照合し、宣言だけが異なる取り違えを拒否する。

交互測定はブロックごとに別VMを起動するため、メモリの増減は各ブロック内の開始・終了を対で調べる。集計処理は`guest_memory_blocks`に各対を残し、`guest_memory_end`には最終ブロックの観測だけを入れる。異なるVMの開始・終了を一つの連続動作とみなさない。この修正前に起動済みのhalfkp-linear-v2比較では、メモリ判断に個々のブロックファイルを使う（一致率の集計には影響しない）。

対応あり比較JSONの`performance`には、ホスト実時間・NPS・ノード数・深さの件数、中央値、10/90パーセンタイルを記録する。通常USIの最後のinfo行と専用診断の最終カウンタは別系列とし、片方にない最終カウンタを通常infoで補わない。同一局面で双方に存在する項目だけ比率を求める。モデル間では探索木も変わるため、このNPS比は診断であり、演算変更の効果の単独証明ではない。整数値と同ノード探索が一致する同一モデルの版で演算を比較し、最後に通常2秒の一致率で選ぶ。

固定の駒得基準は旧ビルド、HalfKP以後はNoPIC等の改善を含むビルドである。両者の比較はエンジン全体の改善として報告し、差の全量をHalfKP特徴量だけの効果と解釈しない。多層構造の比較では同じ推論実装・ビルド条件を使用する。

3候補のquick比較はtiny-v3とtiny-v7がともに90/256、tiny-v5が85/256だった。tiny-v3はNPS中央値5,876、初期空きRAM13,148,160 bytes。tiny-v7との一致局面には互いに24件ずつ違いがあるため、同点だけで同じ挙動とは扱わない。tiny-v5はNPS中央値5,199.5、終了時の空きRAM11,132,928 bytes、swap0だった。いずれも反則・異常終了・時間超過0件。候補間と基準との差は[測定履歴](measurement-history.md)および対応あり比較に保存した。
